# Movaura 许可证自动配 Key

本功能是 Keygate 的可选扩展，默认关闭，支持 `slug=movaura-studio`、`type=desktop` 产品的新签发及管理员手动补配旧许可证。模型请求仍由 Movaura 本机直连 jiji，Keygate 只管理许可证和对应的专属 Key。jiji 基础能力已在 Movaura 项目的 `docs/JIJI_API_ACCEPTANCE.md` 验收；后续使用该基线，不重复付费可行性测试。

## 数据、配置与兼容

增量迁移 `20261111_license_ai.up.sql` 新增以下表及许可证生命周期触发器，不回填旧许可证：

| 表 | 用途 |
| --- | --- |
| `ai_provider_accounts` | 每产品的 jiji 管理账号、加密令牌和启停状态 |
| `ai_plan_settings` | 新许可证签发时复制的分组、月额度、周期限额及公共服务绑定 |
| `license_ai_bindings` | 逐许可证的配置快照、原始月锚点、时区、加密 Key、远程 ID、凭据版本、候选 Key 和同步状态 |
| `license_ai_jobs` | 持久化操作、幂等标识、检查点、尝试次数和脱敏错误 |

v0.1.4-dw.4 起，保存方案会覆盖该方案全部已绑定许可证的分组与额度（包括单独调整值），保留 Key、用量和有效期；未绑定旧证不自动补配。旧证通过单张或批量管理入口补配，不直接改数据库。后台仍只扫描绑定表，其他产品不受影响。

复用现有 `RELEASE_KEY_ENCRYPTION_KEY` 主密钥及其 `PREVIOUS` 轮换配置，HKDF 用途为 `license-ai`，AES-GCM 的附加认证数据分别绑定账号产品 ID 和许可证 ID。数据库和主密钥应按既有备份流程共同保护。服务启动时，有 previous 主密钥则在账号／许可证锁内重加密 AI 凭据；不要在旧实例仍运行时混用不同主密钥。没有加密主密钥时 AI 管理接口返回 503，后台 AI 任务不执行。

方案必须是无宽限期的订阅，已有 `studio.ai_profile` 必须指向 `jiji`、`openai`、`https://api-slb.jiji.cc/v1`。分组 ID 由运营指定，历史测试分组不是生产默认值。总额度至少为 `0.00000001` USD，不接受 0（jiji 中 0 表示无限制）；周期限额为 0 时表示不限制。创建后还会同步精确到秒的 UTC 到期时刻，并读回所有配置。

## 开启顺序

1. 按既有发布流程审查、备份和部署包含迁移的 Keygate；管理网络、署名及 v3 签名版本不变。先保持方案 AI 功能关闭。
2. 产品管理的 **吉吉账号** 中输入当前 access token、refresh token 和 access token 到期时刻，开启后台同步。令牌输入后清空；接口只返回是否配置及状态，不返回令牌。不要把令牌写进公共权益、工单或日志。
3. 确认只填写许可证的新 Movaura 客户端已就绪。再进入月付／年付方案的 **AI 默认配置**，设置分组、月总额度及可选周期限额，并开启新签发自动创建 Key。
4. 签发新许可证，等待许可证详情 **AI 服务** 显示已同步。未取得并验证专属 Key 时创建响应为 `ai_pending: true` 且授权码为空，授权码 reveal 返回 `409 AI_PENDING`；不要作为可交付许可证发送给客户。
5. 配置了 SMTP 时，首次专属 Key 发布与交付邮件入队在同一事务完成，复用现有邮件队列。邮件只包含软件授权码，不包含 jiji Key。管理员也可在准备完成后按原方式查看授权码并交付。
6. 客户在新 Movaura 中只输入授权码。不要升级仍依赖手填 Key 的旧客户，旧许可证可由管理员手动补配，再由 beta7 刷新授权取得 Key。

## 联动与周期

许可证状态、有效期或方案变更与同步任务一起提交到数据库；现有进程每 30 秒处理，客户端激活、验签链路不调用 jiji 管理接口。每许可证的事务锁、行锁保证串行执行；执行前重读最新许可证，撤销后不会被旧任务重新启用。

- 新签发创建专属 Key；文本与视觉共用。修改方案配置同时同步全部已绑定许可证，不清零用量。
- 续费／修改有效期只同步期限和配置，提前续费不清消费。暂停／撤销禁用；恢复仅在许可证当前可用时启用，保留消费。取消订阅后仍在已付有效期内的许可证继续可用。
- 自然到期依靠 jiji 上已同步的精确到期时间拦截；到期同刻不再发放月额度。
- 月付、年付均按原始 `valid_from` 的日期、时刻及签发时 Keygate 计费时区每月重置总已用额度。1 月 31 日 → 2 月末 → 3 月 31 日，不漂移。停机跨多个周期只处理当前周期，不补发错过周期；暂停期间不发放，恢复后只处理当前有效周期。
- 总额度重置与三个周期用量重置独立。耗尽不自动补额。更换 Key 本周期恢复至配置额度，并在发布检查点一并占用当前周期的发放记录，避免下一次扫描再次补满。
- 更换 Key 先建立并验证候选 Key，再禁用并读回旧 Key，最后发布新绑定并递增凭据版本。失败时保留候选及旧绑定供恢复。旧 Key 已停用但新绑定未发布时，客户可能暂时无法调用；不会回退或自动重发模型请求。

## 管理接口

路径前缀均为 `/api/v1/admin`，沿用现有会话／API Key 权限及产品范围检查，所有 AI 响应禁止缓存。

| 方法与路径 | 权限／作用 |
| --- | --- |
| `GET/PUT /products/{id}/ai-account` | 原 admin 权限；配置或查询脱敏账号状态 |
| `GET/PUT /plans/{id}/ai` | 原 admin 权限；保存默认值并覆盖全部已绑定许可证 |
| `GET/PUT /licenses/{id}/ai` | admin 或 `licenses:write`；查询绑定／记录，调整此许可证分组及额度 |
| `POST /licenses/{id}/ai/reset_quota` | 清零总已用额度 |
| `POST /licenses/{id}/ai/reset_rate` | 清零三个周期用量 |
| `POST /licenses/{id}/ai/rotate` | 创建并发布替换 Key |
| `POST /licenses/{id}/ai/retry` | 恢复可安全重试的失败任务，不重放未知重置 |

POST 操作必须携带 `Idempotency-Key`。同一意图重试沿用该值；新额度发放必须是另一次明确操作。页面在网络结果不明时保留同一操作标识。审计记录操作类型及实体 ID，不记录令牌或完整 Key。

授权 v3 令牌新增可选顶层 `ai_credential`，字段为 `version:1`、`provider_id`、`profile_binding`、`revision`、`api_key`。公共 `studio.ai_profile` 不含客户 Key。该附件只通过现有产品／许可证／设备证明与签名授权接口返回；列表、导出、门户和 AI 管理详情没有完整 Key。包含附件的激活响应不会落入原幂等响应缓存，避免将可解码的 Key 间接明文落库；重试仍受原设备证明和激活数量保护。签名不是加密，客户端仍会持有自己的模型调用 Key，不得记录签名令牌正文。

## 失败、恢复与回退

界面区分已同步、处理中、失败、结果待确认。管理接口写入后必须读回验证。只对结果明确的临时只读失败做有上限的自动重试；未知写入停在检查点，禁止无条件重试循环。

- **创建超时**：点击重试后先用 `keygate-<license-id>-g<generation>` 精确名称查询，唯一匹配后恢复。重名、缺 Key、查询不完整或无法找到已发出请求的结果都转人工处理，不再盲目 POST。
- **未知重置**：`phase=reset_sent` 不自动重放。恢复前由管理员核对 jiji 消费、远程 Key ID 和操作时间；并发模型消费也可能导致读回无法证明清零。无法证明时保留待确认，不能假设失败后再次补满。需要解除阻塞时，应在受控数据库维护流程中锁定该许可证，审查并仅确认该任务的结果或放弃本次发放，保留原因、前后证据和审计；本版不提供绕过确认的“一键重置重试”。
- **未知更换**：保留原任务重试；不要另开更换任务，也不要手改绑定覆盖候选。旧 Key 禁用读回成功前不会发布候选。
- **认证异常、其他 429 或封禁**：账号进入需要处理状态，后续任务不发请求。明确 `insufficient_quota` 是额度耗尽业务状态。先确认封禁解除或重新取得当前登录令牌，再录入账号并重试受阻任务；不做冷却探测。
- **登录续期**：账号锁内持久化 `refreshing` 后才请求 `/auth/refresh`，成功加密保存新 access/refresh token 后回到 ready。超时或进程中断留在 refreshing／attention，管理员重新录入凭据；绝不重复使用可能已轮换的 refresh token。
- **服务停用**：关闭账号同步或方案默认配置不会替代禁用已经发放的 Key。暂停／撤销必须检查 AI 同步结果；账号不可用时需在 jiji 人工禁用对应 ID。
- **软件回滚**：先关闭新签发，确认在途创建／重置／更换，并处理已发 AI Key。保留新表、任务和迁移记录，不执行破坏性 down migration。旧二进制不会消费新任务，因此不能把回滚后二次修改许可证当作 jiji 已同步。

跨服务器网络、生产部署、周期限额本身耗尽及长期无人值守需要独立环境验收。代码回归使用隔离 PostgreSQL、合成 HTTP 响应和前端模拟；发布实机验收仅操作专用测试 Key，不调用付费模型。

## 本地验证

Go 定向测试：`go test ./internal/service ./internal/handler ./internal/store ./internal/license ./cmd/server`。AI 数据库集成测试需显式设置 **专用隔离数据库** `AI_TEST_DATABASE_URL`，不得指向生产。先执行 `go test ./internal/service -run '^TestAI'`，再执行 `go test ./internal/handler -run '^TestAI'`；后者读取前者建立的合成记录。测试保留数据便于核查，建议每轮使用新的数据库。

前端执行 `npm run typecheck`、针对改动文件的 Biome 检查及 `npm run build`。验收包括账号输入清空、方案保存、许可证卡片及独立重置确认；浏览器请求全部模拟，不连接生产后台。Movaura 自动凭据的实现与验收见该项目 `docs/LICENSE_AI_INTEGRATION.md`。
